# 可插拔企业问题导航员 · 产品泛化方案（V1 草案）

> 基于《AI 研发问题导航员 · 产品与技术实施方案 V1》泛化而来
> 文档状态：内部产品讨论稿 ｜ 版本 V0.1 ｜ 2026-08-05
> 适用范围：从"单一公司研发问题导航"泛化为"可灵活插拔的企业内部问题导航平台"

---

## 1. 一句话定位

**企业内部问题诊断导航系统**：一个企业无关的问题诊断内核 + N 个可插拔的企业系统连接包。让企业员工用自然语言描述内部问题（代码异常、设备告警、理赔卡单、流程卡点），系统自动连接该企业的知识源与系统，给出"涉及什么对象、什么关系、按什么顺序排查、证据可信度如何"的导航式答案。

> 品类声明：**这是一套问题诊断导航系统，不是一个知识库。** 知识库帮你"存和找"文档；我们帮你"查和诊"——出了问题，去哪查、按什么顺序查、每条证据有多可信。这是两个不同的品类。
>
> 同时，这不是一个行业解决方案，而是一个企业级解决方案——同一个内核，连接同一个企业内不同的内部系统。行业只是"连接包"的接入场景，不是产品的定位。

内核是水平的（编排、检索、知识图谱、证据体系），企业系统连接包是插件（连接器、实体、关系、诊断规则包）。**先做透一个企业场景（金融研发），再用第二个企业场景（药企）证明"可插拔"。**

---

## 1.1 价值内核（Vision / 价值假设）

> **使用者只管"描述问题"，我们负责"给出解决方案或查询路径"。**
> **系统越是庞杂、越是经久难查，这套产品的提效就越大。**

这是产品的根本定位，也是选型的唯一标尺：

- **输入极简**：用户用自然语言描述现象（"授信接口又 500 了""某批记录偏差超限"），不需要知道知识存在哪、怎么连。
- **输出是"路径"而非"答案"**：给出"涉及哪些对象 → 它们之间什么关系 → 按什么顺序查 → 每条证据可信度几何"的导航，把人从"在系统间手动拼因果链"中解放出来。
- **价值与复杂度正相关**：扁平、文档齐全、人人都熟的系统，用了也难感知差异；真正吃价值的是**多仓库、多系统、多年累积、关键人离职后就没人说得清**的"黑暗知识"——这正是庞杂遗留系统的常态。复杂度越高，首次定位时间越长，导航员省下的时间越多，ROI 越明显。

> 推论：行业只是"复杂度的一种来源"，不是产品的定位。本产品是**企业级**解决方案——同一个内核，连接同一个企业内部的不同系统，让它们可被统一导航。金融研发和药企系统只是"够乱够复杂"的两个接入点，不是"我们做行业方案"。

---

## 1.2 核心竞争力（护城河分层）

**一句话**：把"企业里没人能说清的系统"变成"可导航的系统"，而且只做这一件事。

四层递进，越往上越难被抄：

| 层 | 名称 | 内容 | 为什么难抄 |
|---|---|---|---|
| ① | **品类错位（认知层）** | "诊断导航，不是知识管理"——专为没人维护的"黑暗知识"而生，不靠文档齐整 | 大厂（Confluence/Glean/Sourcegraph）的产品架构与商业模式假设"知识应被维护"；我们恰恰服务"没人维护的乱系统"。错位竞争，非正面竞争 |
| ② | **证据体系（信任层）** | 4 档可信度（源码→配置→推算→推测）、防幻觉硬约束、权限前置过滤 | 金融/药企是重监管行业，采购与安全团队会问"AI 凭什么让我信你"——证据体系就是答案；这需要真实场景打磨，非一朝一夕 |
| ③ | **锁定效应（切换成本）** | 排查 SOP 跑在导航员上、接了内部系统、存了配置与规则包 | 换掉 = 重做集成 + 重新教所有人排查；垂直规则包（信贷排查路径、PV 信号溯源）需懂业务的人写，抄不走 |
| ④ | **成本结构（solo 优势）** | 一人公司成本结构，私有化部署 + 实施服务 | 价格能打到比大厂 SaaS 低很多，实施服务吃行业 know-how、毛利高 |

**伪壁垒（别当卖点）**：连接器框架（已商品化，Sourcegraph/Glean/Cursor 都在做）；客户数据（知识图谱建在客户侧，是客户的资产）；"支持所有系统"泛化（是杠杆，不是壁垒）。

**压力测试**：*如果我现在停手半年，竞争者抄我的产品，他缺什么？* 缺"重监管场景的验证案例"（要时间 + 信任）、缺"嵌进客户流程后的规则包"（要客户）、缺"对'乱系统'这个场景的专注"（大厂不愿砍主线做）。缺的才是护城河。

## 2. Problem Statement（为什么做）

企业内部知识高度碎片化：代码散在多仓库、配置散在多工作台、设备/工单/保单/流程散在不同系统。员工遇到问题时，靠个人经验和对"熟人的记忆"在系统间手动拼因果链——首次定位时间长、易漏层级、且无法规模化复制。

原 PDF 已验证：**在研发场景，问题不是"搜不到代码"，而是"跨仓库/跨配置层难以建立完整因果链"**。同一痛点存在于药企（LIMS/ELN→法规→不良反应信号）、制造（设备→工单→工艺）、保险（保单→规则→理赔）、政务（事项→材料→流程）等几乎所有行业——只是"知识源"和"行业实体"不同。

**更本质的观察（价值内核的佐证）**：这套工具的价值与系统复杂度成正比。越是"庞杂 + 经久难查"的系统（历史包袱重、系统多、关键人依赖强），员工单次排查的耗时与不确定性越高，导航员能压缩的首次定位时间（MTTL）也越大。**我们不为"整洁的小系统"而生，我们为"乱而难查的大系统"而生。**

**不解决的代价**：新人上手慢、依赖关键人、问题复发率高、专家时间被重复咨询消耗。

## 3. Goals（目标）

1. **V1 验证单一垂直切口**：金融/信贷研发问题导航包上线，黄金问题集首答命中率 ≥ 80%，用户首次定位时间较人工下降 ≥ 50%。
2. **内核与企业系统解耦**：V1.5 完成"连接器 SDK + 实体/关系注册机制"，使新增一个企业系统连接包无需改动内核代码。
3. **V2 证明可插拔**：上线第二个**跨行业**插件（药企问题导航包），证明同一内核可服务非研发场景。
4. **商业化验证**：以"私有化部署 + 实施服务"拿到首个付费客户（或内部落地），形成可复制的行业包交付模板。
5. **OPC 落地**：入驻德阳/成都 OPC 社区，拿到词元券/算力券资格，作为一人公司的种子项目与作品集。

---

## 4. Non-Goals（明确不做）

1. **不做"泛行业通用平台"的空壳**：V1 不承诺同时服务多个行业，必须先有一个付费/验证中的垂直切口。（避免水平平台陷阱）
2. **不做自动执行/自动改配置/自动发 PR**：保持"导航员"定位——给出证据与排查顺序，最终动作由人确认。（继承原 PDF 的防风险原则）
3. **不把客户数据当自有资产经营**：知识图谱建在客户侧，护城河在诊断引擎与行业包，不在数据本身。
4. **不重造已被商品化的基础能力**：代码解析（Tree-sitter）、向量检索（pgvector）直接用成熟方案，不在其上过度投入；差异化压在"诊断编排 + 行业规则包"。
5. **不引入复杂图数据库/多 Agent/搜索集群**（V1-V2）：PostgreSQL + pgvector + FTS 满足 MVP；扩展触发条件见 §9。
6. **不碰自主无限推理**：保持受约束的单 Agent 编排，检索权限前置过滤，防幻觉硬约束不变。

## 5. 架构：水平内核 + 企业系统连接包（两层）

### 5.1 水平内核（企业无关，V1 即建设，长期不变）

| 模块 | 职责 | 与 PDF 对应关系 |
|---|---|---|
| **Query API + 权限 + 会话** | 入口、租户隔离、权限前置过滤 | PDF §9.1 |
| **查询编排器** | 分类 / 实体提取 / 检索计划 / 证据校验 | PDF §9.1 编排器 |
| **混合检索引擎** | 精确 / 词法 / 向量语义 / 关系扩展 / 业务词典 | PDF §6.3 |
| **知识图谱存储** | 实体 + 元数据 + 关系边 + 配置目录（通用 schema） | PDF §10 |
| **连接器框架（SDK）** | 统一接口：`connect / extract / sync / permissions`——**核心插拔点** | 泛化自 `connectors/git`、`connectors/workbench` |
| **实体/关系注册机制** | Entity Registry + Relation Registry，行业包在此登记新类型 | 泛化自 PDF §10.1/§10.2 |
| **诊断编排器** | 受约束编排 + 证据包 + 回答约束（4 档可信度） | PDF §8、§12 |
| **评估框架** | 黄金问题 / 链路 / 配置 / 报告 | PDF `evaluation/` |

### 5.2 企业系统连接包（插件，每套企业系统一个包）

每个企业系统连接包 = 一组"注册到内核"的工件（连接器、实体、关系、规则包）：

| 工件 | 内容 | 示例（金融研发包 / 制造设备包） |
|---|---|---|
| **连接器实现** | 实现连接器 SDK，接入该行业知识源 | git+workbench / IoT+CMMS 工单系统 |
| **实体扩展** | 在 Entity Registry 登记行业实体 | CodeSymbol、ConfigItem / 设备、传感器、工单 |
| **关系扩展** | 在 Relation Registry 登记行业关系边 | CALLS、READS_CONFIG / 触发、依赖、归属 |
| **业务词典 / 诊断规则包** | 痛点 → 排查路径映射，行业专属 | 授信→loading→配置开关 / 报警→停机→工艺参数 |
| **黄金问题集** | 行业验证集，衡量首答命中率 | PDF §4.2 S1–S7 / 设备故障 10 题 |
| **配置接入分级适配** | L1–L4 接入策略对齐行业系统 | workbench L1–L3 / IoT 只读 API L3 |

> **关键判断**：内核只认"实体 + 关系 + 连接器接口"，不认行业。新增行业 = 写一个包并注册，不碰内核。这正是原 PDF "架构可扩展、任务不扩张"原则的泛化落地。

## 6. V1 垂直切口：金融/信贷研发导航包（Pack-FinR&D）

V1 直接复用原 PDF 的 V1 作为第一个行业包（这也是作者最熟悉的领域，具备"垂直纵深"护城河）。

- **知识源**：小程序仓库、Load Server 仓库、调度服务仓库、配置工作台目录（L1–L3）
- **核心实体**：Repository / SourceFile / CodeSymbol / ApiEndpoint / Page/Route / Task / ConfigItem / ErrorCode / BusinessTerm / ExternalBlackbox
- **诊断能力**：页面→API→服务→调度→配置的调用链与影响链；4 档可信度回答；防幻觉硬约束
- **首期用户**：前端/联调/线上排查开发、新加入项目开发、技术负责人
- **交付形态**：私有化部署（企业内网）或作者自用作品集；Web 问答 + 索引管理

**V1 验收（黄金问题集）**：S1–S7 类问题首答命中率 ≥ 80%，引用必须带 Commit/配置作用域，推测不得写成事实。

## 7. V2 证明可插拔：第二个行业包（药企导航包 / Pharma Pack）

选药企的理由：① 与原研发场景差异足够大（知识源从代码变为 LIMS/法规/PV，实体从函数变为化合物/试验/不良反应），能真正证明内核泛化；② **成都天府国际生物城是国家级生物医药集群**，作者可到生物城实地接触药企、共建领域知识与找早期内部落地客户——领域入口已具备；③ 受监管行业（GxP/CSV/数据完整性）**最吃本方案"4 档可信度 + 防幻觉 + 权限前置"的证据内核**，溢价与切换成本最高。

- **连接器实现**：LIMS/ELN（实验数据）、CTMS/EDC（临床试验）、法规文档库（NMPA/FDA PDF 解析）、PV 不良反应库、专利/文献检索
- **实体扩展**：化合物/药品(Drug)、适应症(Indication)、临床试验(Trial)、受试者(Subject)、SOP/批记录(SOP/Batch)、不良反应事件(AE)、法规条款(Regulation)
- **关系扩展**：治疗(药物→适应症)、纳入(试验→受试者)、符合(批次→SOP)、关联(不良反应→药物)、适用(法规→产品线)
- **诊断规则包**：不良反应信号溯源（PV）、法规适用性判断（条款→产品线）、变更影响链（SOP 变更→工艺/系统）
- **黄金问题集**：药企 10 题（如"某化合物的历史体外实验数据在哪？""某不良反应信号可能关联哪些在研药物？""某 SOP 变更影响哪些工艺和系统？"）

> **领域接入策略**：复用 V1"内部开源 + 协作者共建"模型——到天府国际生物城接触药企，与药学 SME 共建诊断规则包、找首个内部落地客户。规则包即护城河，SME 共建是护城河的制造方式。
>
> 完成 V2 即证明一句话："换一套连接器 + 一组实体/关系注册 + 一个规则包，内核零改动能服务新行业。" 这比空喊"支持所有行业"有说服力十倍。

## 8. 用户故事（按角色）

**行业包开发者 / 作者（OPC 主理人）**
- 作为行业包开发者，我希望用连接器 SDK + 注册机制定义新行业包，以便不改动内核就能上线新行业。
- 作为 OPC 主理人，我希望每个包有独立黄金问题集与评估报告，以便量化该包的诊断质量。

**企业内部员工（终端用户）**
- 作为研发，我希望描述"授信提交一直 loading"，以便快速拿到涉及的页面/接口/服务/配置与排查顺序。
- 作为设备工程师，我希望描述"工位频繁报警停机"，以便拿到可能的设备/工单/工艺变更与排查顺序。
- 作为新员工，我希望系统给出带证据可信度的答案，以便不依赖熟人口述也能独立排查。

**企业 IT / 采购（买家）**
- 作为 IT 管理员，我希望权限在检索前过滤、数据留存在内网，以便满足安全与合规要求。
- 作为采购，我希望看到可复制的交付模板与行业包清单，以便评估扩展成本。

## 9. 需求分级

### P0（V1 必须）
- 查询编排器（分类/实体提取/检索计划/证据校验）✅ 沿用 PDF 设计
- 混合检索（精确/词法/向量/关系扩展/业务词典）
- 知识图谱存储（PostgreSQL + pgvector + FTS）与关系边建模
- 金融研发包全部实体/关系/规则包/黄金问题集
- 4 档可信度 + 防幻觉硬约束 + 引用带 Commit/作用域
- 权限前置过滤、私有化部署能力

### P1（V1.5–V2）
- **连接器 SDK + 实体/关系注册机制**（解耦内核与行业）⭐ 本方案核心；药企包会逼出"文档/PDF 类连接器"与"强监管权限模型"两类通用抽象
- 药企包（证明可插拔，领域入口：天府国际生物城）
- 配置接入 L3 只读 API（读取当前值与历史）
- 评估框架产品化（黄金问题自动跑分 + 报告）

### P2（Later）
- 多行业包市场与交付模板标准化
- 运行时配置解析 L4（结合用户/产品/渠道计算最终生效值）
- SaaS/订阅形态探索（需先解决多租户与安全）
- 复杂图数据库/独立向量库（仅当仓库数十个、关系边规模显著增长、检索成瓶颈时，见 PDF §9.3 升级触发条件）

## 10. 成功指标

**北极星指标**：单次问题导航为企业节省的"首次定位时间"（Mean Time To Locate, MTTL）较人工基线下降比例。

| 类型 | 指标 | 目标 |
|---|---|---|
| 领先 | 黄金问题集首答命中率 | V1 ≥ 80%，V2 ≥ 75% |
| 领先 | 问答采纳率（用户标记"有用"） | ≥ 70% |
| 领先 | 行业包上线数 | V1=1，V2=2（跨行业） |
| 滞后 | 内部落地采用度（采用团队数 / 月活跃排查人次） | V1 末 ≥ 2 团队；V2 末 ≥ 1 外部或跨 BU 落地 |
| 滞后 | 客单价（实施+订阅） | V2 后形成可复制报价模板 |
| 滞后 | 行业包扩展率 | 单公司/单客户增购第 2 个包 |
| 健康 | 防幻觉率（推测误判为"已确认"比例） | ≤ 2% |
| 健康 | 索引时效（代码/配置变更到可检索延迟） | ≤ 24h |

## 11. 风险与缓解

| 风险 | 说明 | 缓解 |
|---|---|---|
| 水平平台陷阱 | 过早喊"泛行业"导致无付费标杆 | 死守 V1 单切口，V2 才跨行业 |
| 企业销售重、solo 难扛 | 采购/安全/私有化门槛高 | 从实施服务切入 + 轻量私有化；先作品集/内部落地引流 |
| 护城河误判 | 把客户数据当自有资产 | 护城河聚焦诊断引擎 + 行业规则包 + 切换成本 |
| 竞品商品化 | Sourcegraph/Glean/Cursor 做基础能力 | 差异化在行业诊断深度，不在解析/检索 |
| 合规/数据出境 | 企业数据敏感 | 私有化 + 权限前置过滤 + 不碰生产写操作 |
